# テスト運用

このプロジェクトのテストの置き場所・書き方・粒度と、現在あるテストの一覧をまとめる。

- 実体は `record/tests/`
- 実行は リポジトリルートの `./run_tests.sh`

---

## 1. 何のためのテストか

**ヘッドレスで回せるロジックの回帰検出**が目的である。Godot をウィンドウなしで起動し、実際にノードを生成して物理フレームを進め、状態を検証する。

このテストで**分かること**と**分からないこと**をはっきりさせておく。

| 分かる | 分からない |
|---|---|
| 状態遷移・データの受け渡し・計算結果 | 見た目の良し悪し、色や余白の妥当性 |
| ノードの構成、シグナルの接続 | 操作感、パズルとして面白いか |
| レイアウトの数値（サイズ・座標・はみ出し） | 実際の描画結果（`_draw()` は走らない） |
| プロセスをまたぐファイルの受け渡し | エディタプラグインの実挙動（ボタンの見た目・押下） |

**テストが通ること＝正しく動くこと、ではない。** ゲームの挙動は最終的にプレイして確認する。エージェントが確認できない場合は、何を人間に見てほしいかを明示して報告すること。

---

## 2. 実行方法

```bash
./run_tests.sh
```

- `record/tests/` 直下の `test_*.gd` を**すべて**実行する（ファイル名順）
- 1件でも失敗すれば **exit 1**。全部通れば exit 0
- Godot の場所は `GODOT` 環境変数で上書きできる
  ```bash
  GODOT=/path/to/godot ./run_tests.sh
  ```

出力の末尾に必ず次の行が出る。この行が無い場合は途中でハングまたはパースエラーが起きている。

```
TEST SUMMARY: pass 76 / fail 0
```

### 仕組みの注意点

- **シーンとして起動している**（`--script` ではない）。カスタム MainLoop では Autoload（`GameManager` など）が登録されず、参照するテストがコンパイルに失敗するため
- `--quit-after` でフレーム数の上限を掛けてある。パースエラーでランナーが起動しないと `quit()` に到達せず永久に走り続けるための保険

## 3. 置き場所とファイル構成

```
record/tests/
├── TestRunner.tscn / TestRunner.gd   # ランナー。test_*.gd を集めて順に実行する
├── Assert.gd                         # アサーションと集計
├── test_*.gd                         # ← テストはここに置く。この名前でないと拾われない
└── helpers/                          # テストから使う補助スクリプト（自動実行されない）
```

**ルール**

- テスト本体は `record/tests/` の**直下**に `test_<対象>.gd` の名前で置く
- 補助スクリプトは `helpers/` に入れる。`test_` で始まらないので自動実行されない
- 1ファイル ＝ 1つの対象。対象が違うものを同じファイルに混ぜない

## 4. テストの書き方

```gdscript
## <何を確かめるテストか>を1〜2行で書く。
extends Node

const TestAssert := preload("res://tests/Assert.gd")

func run_tests(t: TestAssert) -> void:
	t.ok("条件を満たす", 1 < 2)
	t.eq("値が一致する", 1 + 1, 2)

	await get_tree().physics_frame  # 物理を進めたいときは await してよい

	t.done()  # ← 必ず最後に呼ぶ
```

| 使うもの | 用途 |
|---|---|
| `t.ok(ラベル, 条件, 詳細)` | 真偽の確認。`詳細` は失敗時の手がかりに使う |
| `t.eq(ラベル, 実際, 期待)` | 値の比較。失敗時に両方の値が出る |
| `t.done()` | **必須**。最後に呼ぶ |

### `t.done()` が必須な理由

GDScript の実行時エラーは例外にならず、その場で関数を抜けるだけである。マーカーが無いと「テストが途中で死んだのに成功扱い」になる。実際にこの穴で RED が静かに通り抜けた事故があったため、ランナーは `done()` の未到達を失敗として報告する。

### Autoload の後始末

Autoload はテスト間で生き続ける。`GameManager.current_state` などを触ったテストは、最後に元へ戻すこと。戻さないと次のテストが落ちる。

```gdscript
GameManager.current_state = GameManager.GameState.MAIN_MENU
GameManager.input_locked = false
LoopManager.ClearAll()
LoopManager.set_spawn_parent(null)
WorldResetManager.set_level(null)
```

## 5. どの粒度で書くか

**「壊れたら気づきたいが、目視では気づきにくいもの」**を書く。

### 書く

- **不変条件**（[AGENTS.md](../AGENTS.md) の「絶対に壊してはいけない不変条件」）。壊れると再生が破綻するが、症状が出るまで気づきにくい
- **状態遷移の分岐**。「予約があれば直行、無ければタイトル」のような if の両側
- **境界値**。上限・下限でのクランプ、0件、上限超え
- **回帰**。一度壊れたものは必ずテストにする（見切れ・レイアウトなど見た目でも数値で測れるなら書く）

### 書かない

- 一度きりの動作確認。使い捨てスクリプトで確かめて消す
- Godot 標準の挙動そのもの
- 見た目の良し悪しなど、数値で表せない judgement

### 粒度の目安

1ファイルに 5〜30 アサーション程度。それを超えるなら対象が広すぎるので分割を検討する。

| `test_harness.gd` | 3 | ハーネス自身の自己確認（発見・実行・`await`・集計） |

| `test_debug_menu.gd` | 28 | メニューの開閉と `input_locked` 連動 / 演出中は開かない / ショートカットの差し替え / 登録 API 6種 / パネルのレイアウト（画面を覆わない・はみ出さない・折り返す） |

### 何を見たいときにどれを使うか

| 見たいこと | 使うもの |
|---|---|
| 変更が既存を壊していないか | `./run_tests.sh`（全部） |
| デバッグ起動が F5 に漏れていないか | `test_debug_launch.gd` / `test_main_debug_launch.gd` |
| メニューに項目を足して壊れていないか | `test_debug_menu.gd`（登録 API とレイアウト） |
| メニューからの操作がゲームに効いているか | `test_debug_menu_items.gd` |
| プラグインがエディタで読めるか | `test_debug_plugin.gd` |
| ハーネス自体が動いているか | `test_harness.gd` |

## 7. 現状の穴

**テストはデバッグ機能に偏っている。ゲーム本体のテストはまだ無い。**

未カバーで、書く価値が高いと考えられるもの:

- **録画と再生の一致**（`InputFrame` → `GhostController` → 同じ軌道になるか）。設計の核心なので最優先
- **ゴーストの一方向衝突**（`LoopManager._set_ghost_collision()` のマスク計算）
- **ギミック**。滑車は開発時にヘッドレスで検証したが、使い捨てだったのでテストとして残っていない
- **ワールドリセット**（`WorldResetManager` の再帰走査）

これらは実装が固まっているぶん壊れにくいが、壊れたときの被害が大きい。手を入れる予定ができた時点でテストを先に足すのが望ましい。
